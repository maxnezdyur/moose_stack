Summary

Purpose

Provide the rigid body modes (RBMs) as an algebraic-multigrid near-null-space so free / under-constrained solid-mechanics solves converge under both PETSc GAMG and hypre BoomerAMG — including multiphysics thermo-mechanical models that carry a temperature degree of freedom (DOF) in the same nonlinear system as the displacements.

Problem

The framework near-null-space plumbing already exists but is dormant: setting near_null_space_dimension allocates ghosted vectors NearNullSpace_0..N-1 (framework/src/problems/FEProblemBase.C:818-827) that FEProblemBase::computeNearNullSpace (FEProblemBase.C:8182-8194) hands to PETSc via libMesh's MatSetNearNullSpace (wired at framework/src/systems/NonlinearSystem.C:110). But no object fills those vectors, no input uses them, and nothing documents them. The only historical filler, RigidBodyModes3D, was deleted (commit 237df2ac225, "Remove unused"). Without RBMs in the near-null-space, AMG coarse grids cannot represent the low-energy rigid modes and free-body elasticity converges slowly or stalls. PETSc's automatic coordinate path (MatNullSpaceCreateRigidBody / PCSetCoordinates) is not a substitute here: it assumes block size = spatial dimension, which is false the moment a temperature DOF is present.

Solution

Add a dimension-general RigidBodyModes NodalUserObject in modules/solid_mechanics that assembles the full block near-null-space of a coupled system. It writes the rigid body modes into the displacement DOFs (with every non-displacement DOF left at zero in those modes), and adds one constant mode for each additional field variable named in a new constant_mode_variables parameter — temperature and any other diffusion-like scalar. Each constant mode is 1 on that variable's DOFs and 0 everywhere else. This is required for correctness: a heat-conduction (Laplacian) block has the constant function as its low-energy near-null-space mode, so zeroing the temperature DOFs would leave AMG with no coarse-grid representation of the thermal block and degrade its convergence. The near-null-space dimension is therefore N = n_rbm + constant_mode_variables.size() (n_rbm = 3 in 2D, 6 in 3D).

The object self-registers the near-null-space through a small new public framework method FEProblemBase::initNearNullSpaceVectors(dim), so no manual [Problem]/near_null_space_dimension is ever required. A convenience flag rigid_body_near_null_space = true on the [Physics/SolidMechanics/QuasiStatic] action adds the object automatically and forwards the action's temperature variable as a constant mode. The object is solver-agnostic: GAMG consumes the near-null-space automatically; hypre consumes it once the input file sets the BoomerAMG interpolation-vector options. Preconditioner topology is monolithic (one matrix; the mechanical and thermal modes are packed into disjoint DOF blocks of the same vectors) — the confirmed convention for coupled thermo-mechanical models.

Physics & Signature

U1 — framework plumbing (no physics). The near-null-space is a set of ghosted system vectors NearNullSpace_0..N-1 handed to PETSc as-is. initNearNullSpaceVectors(dim) only allocates those vectors and records N = dim; it computes no field quantity.

U2 — the rigid body modes

For a node at reference position (x,y,z)(x,y,z)(x,y,z), each rigid body mode is a displacement field the object writes into one near-null-space vector. In 3D there are 6 modes (3 translations + 3 rotations); in 2D there are 3 (2 translations + 1 rotation). The rotations are taken about the origin — with the translations included, any origin spans the same rigid-body subspace, and GAMG / BoomerAMG orthonormalize the supplied vectors internally.

Translations (3D): ϕtx=(1,0,0), ϕty=(0,1,0), ϕtz=(0,0,1)\phi_{t_x}=(1,0,0),\ \phi_{t_y}=(0,1,0),\ \phi_{t_z}=(0,0,1)ϕtx​​=(1,0,0), ϕty​​=(0,1,0), ϕtz​​=(0,0,1).

Rotations (3D): ϕrx=(0,−z, y), ϕry=(z,0,−x), ϕrz=(−y, x,0)\phi_{r_x}=(0,-z,\,y),\ \phi_{r_y}=(z,0,-x),\ \phi_{r_z}=(-y,\,x,0)ϕrx​​=(0,−z,y), ϕry​​=(z,0,−x), ϕrz​​=(−y,x,0).

2D reduces to ϕtx=(1,0), ϕty=(0,1), ϕrz=(−y, x)\phi_{t_x}=(1,0),\ \phi_{t_y}=(0,1),\ \phi_{r_z}=(-y,\,x)ϕtx​​=(1,0), ϕty​​=(0,1), ϕrz​​=(−y,x).

DOF placement (the "don't mix up DOFs" contract). Two disjoint kinds of mode share the same near-null-space vectors, each writing only its own DOF block.

  • Rigid body modes (indices 0 .. n_rbm-1): at a node whose displacement DOF indices are d_x, d_y, d_z (from dof_number(sys, disp_var, 0)), the object sets NearNullSpace_m[d_i] = (phi_m)_i and touches nothing else. Every temperature, scalar, or multiplier DOF keeps the zero it was allocated with in these modes.
  • Constant modes (indices n_rbm .. n_rbm + n_const - 1): for the k-th constant_mode_variables entry, the object sets that variable's DOF to 1.0 at every node it lives on and leaves all other DOFs (including displacements) at zero. This is the correct near-null-space of a diffusion (heat-conduction) block: its lowest-energy mode is the constant function, so AMG needs it to build a good coarse temperature space.

The result is a block-diagonal set of modes — mechanics in the displacement rows, one constant per scalar field in its own rows, no cross-bleed. This is exactly why the explicit-vector approach is required: for a coupled node the DOF layout is (disp_x, disp_y, disp_z, T), so the block size is dim+1 ≠ dim, and PETSc's MatNullSpaceCreateRigidBody / PCSetCoordinates (which assume block size = dim) would build wrong modes that bleed into T and cannot express a separate constant temperature mode at all.

intended execute() per locally-owned node
if (node.processor_id() != processor_id()) return;

// -- rigid body modes: displacement DOFs only --
if (node.n_dofs(sys, disp_var[0]) > 0)
  for (m = 0; m < n_rbm; ++m) {      // 3 (2D) or 6 (3D)
    auto & v = sys.getVector("NearNullSpace_" + m);
    v.set(dof_x, phi[m].x);
    v.set(dof_y, phi[m].y);
    if (ndisp == 3) v.set(dof_z, phi[m].z);
    // T / scalar DOFs untouched here -> 0 in the rigid modes
  }

// -- constant modes: one per constant_mode_variable (e.g. T) --
for (k = 0; k < cvars.size(); ++k)
  if (node.n_dofs(sys, cvars[k]) > 0) {
    auto & v = sys.getVector("NearNullSpace_" + (n_rbm + k));
    v.set(dof_number(sys, cvars[k], 0), 1.0);   // that block only
  }

Questionables

Fully free vs minimally constrained test body (singular system)

A fully free body has a singular stiffness matrix; near-null-space alone will not make the Krylov solve converge. Assumption: test bodies are minimally constrained (or use null_space_dimension scaffolding) so the solve is well-posed while still exercising the RBM near-null-space. Exact BCs finalized at build.

gtest DOF-safety wiring cost (T2)

Building a coupled disp+temperature system with NearNullSpace vectors in MooseObjectUnitTest may be heavy. If impractical, fall back to a regression assertion — e.g. a small postprocessor summing |NearNullSpace_i| over temperature DOFs (must be 0).

hypre BoomerAMG option values

Start with -pc_hypre_boomeramg_nodal_coarsen 6, -pc_hypre_boomeramg_vec_interp_variant 1, -pc_hypre_boomeramg_interp_type ext+i. Exact values may need tuning for convergence on the chosen mesh.

Self-registration as a constructor side-effect

The UO adds solver vectors from its constructor. This is slightly unusual, but the add_user_object task is the confirmed window before es().init(). The alternative (do it in initialSetup) would rely on libMesh late-allocation of vectors.

execute_on default = initial

Modes derive from reference coordinates, so a single initial fill is correct for small strain. Finite-strain runs do not refresh the near-null-space; acceptable because the near-null-space is approximate by nature.

Notes

Mechanism, end to end

Setup (UO ctor or Action) → initNearNullSpaceVectors(N) allocates NearNullSpace_0..N-1, N = n_rbm + n_const → UO execute() fills the rigid modes on displacement DOFs and one constant mode per constant-mode variable (each mode zero outside its own block) → computeNearNullSpace collects the vectors → libMesh MatSetNearNullSpace on the Jacobian → GAMG uses it automatically / hypre uses it with the BoomerAMG vec-interp options.

Why this is the right shape for thermo-mechanics

A nonlinear temperature variable shares the monolithic system, so each node carries (dispx,dispy,dispz,T)(\text{disp}_x,\text{disp}_y,\text{disp}_z,T)(dispx​,dispy​,dispz​,T). The object never writes TTT, so the rigid-body modes have zero temperature content — correct, since rigid motion changes no temperature. But the temperature block is a diffusion (heat-conduction) operator, whose own lowest-energy near-null-space mode is the constant function. So the object adds one extra vector that is constant on the temperature DOFs and zero on the displacements. The full near-null-space is the direct sum: rigid modes for the mechanical block, a constant for each scalar block, packed into disjoint DOF rows of the same vectors. The coordinate-based PETSc RBM path cannot express any of this (it assumes block size = dim and has no notion of a constant temperature mode), which is the core reason a dedicated DOF-aware object is needed.

  • PCFieldSplit with RBMs on the mechanical block — more robust separation but needs new plumbing to attach a near-null-space to a sub-block; not the solid_mechanics convention.
  • Reviving RigidBodyModes3D verbatim — its subspace_name/subspace_indices/modes API is clunky and 3D-only.
